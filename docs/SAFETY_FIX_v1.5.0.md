# v1.5.0 保護路徑修正紀錄

## 已修正的行為

舊的本機分組可使用保護子目錄中的副本作為唯一 keeper，使所有外層副本成為候選。
資料夾分組也可能以資料夾時間覆蓋個別檔案的最舊 keeper。這不符合保護子目錄與外層原檔均需保留的政策。

修正位於 `grouping.py`、`models.py` 與 `local.py`：最舊外層副本獨立保留；每個操作攜帶保護路徑，
於計畫建立、執行前及刪除邊界拒絕違規目標。整資料夾不能包含任何保留檔，包含未列為清理候選的空檔。
含 hard link 的資料夾不列為整資料夾候選，避免實體識別去重掩蓋其他路徑的原檔。

## 驗證證據

- 獨立唯讀調查重現保護副本取代外層 keeper、資料夾時間與檔案時間衝突，以及單項批次失去保護資訊的途徑。
- 修正後的獨立唯讀複核另外重現空檔 keeper 與 protected hard-link alias 邊界；已補上禁止條件。
- `tests/test_protection_regression.py` 覆蓋以上案例、大小寫與 `..` 別名、單項執行及直接建立計畫。
- 合法控制案例：保護副本、外層最舊原檔均保留，另外兩份外層副本仍可透過正常垃圾桶流程處理。
- 測試只用生成的臨時資料與記錄式刪除介面，未刪除使用者真實檔案。
- 原有 keeper、系統路徑、掃描後變更、垃圾桶失敗不轉永久刪除、CSV 與 GUI 回歸測試一起執行。

## 仍然存在的限制

使用者提供的舊 CSV 不包含 keeper 欄位，無法單憑該紀錄證明歷史畫面上哪個項目被標為原檔。
本次修正有合成資料重現與程式邊界證據，不推測使用者的檔案內容。未執行復原，亦未將私人 CSV 放入 repository。

重新驗證並非跨整棵資料夾的原子交易。Windows 回收筒與 Google Drive API 在驗證後仍可能遇到外部程式寫入；
應關閉寫入程式或暫停同步後清理。未宣稱消除所有 TOCTOU 風險。
